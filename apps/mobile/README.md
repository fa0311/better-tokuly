# Tokuly mobile

Expo SDK 58 (React Native 0.88, New Architecture) · Expo Router · NativeWind ·
MapLibre Native · VisionCamera · expo-video · TanStack Query · Connect RPC.

Development builds, not Expo Go: the native projects are generated by
`expo prebuild` from [`app.config.ts`](app.config.ts) (Continuous Native
Generation) and are not checked in. Everything native is a config plugin there.

```sh
pnpm install
pnpm --filter @tokuly/api run generate          # TypeScript API from proto/
pnpm --filter @tokuly/mobile android            # build and install the dev client (or `ios`)
pnpm --filter @tokuly/mobile start              # Metro for the installed dev client
```

**The server.** `EXPO_PUBLIC_TOKULY_URL` (read at build time) is the one
origin the app talks to: `/api`, `/rt/ws` via the realtime endpoints, `/media`,
`/tiles`, `/map-assets`. The default, `http://localhost:3000`, is the web dev
server, which forwards all of them to the dev API: on an Android device or
emulator run `adb reverse tcp:3000 tcp:3000` (the iOS simulator shares the
host's localhost). Against the Compose stack from an emulator use
`EXPO_PUBLIC_TOKULY_URL=http://10.0.2.2`. A plain-HTTP URL turns on cleartext
traffic in the Android build; an HTTPS one does not.

## Layout

```
app/                 Expo Router routes, thin: (auth) signed out, (app) signed in, (app)/(tabs)
src/features/<area>/ one folder per product area: screens, components, hooks, stores
src/seams/           where features plug into the app (see "How a feature plugs in")
src/platform/        the device: secure storage, install ID, location and the background task, file transfers
src/lib/             the API client, realtime, the query client, i18n, theme, config
src/components/      small native primitives (Button, TextField, Avatar, Page)
modules/             local Expo modules (native code of our own): tokuly-trim, tokuly-web-data
maestro/             end-to-end flows (Maestro), their scripts and fixtures
```

## Shared with the web

Logic comes from `packages/` (see [`packages/README.md`](../../packages/README.md)):
query keys and options, domain rules and formatting from `@tokuly/core`,
strings from `@tokuly/i18n` (the phone's own screens are its `mobile`
namespace), the API and its session from `@tokuly/api`, the realtime client
from `@tokuly/realtime`. The UI is written for the phone: nothing is imported
from `apps/web`, no component is shared with it. When the app needs logic
that is still in `apps/web`, it moves to the shared package first (pure, with
its tests) and the web switches to it.

## How it works

- **Sessions.** Bearer tokens: the access token in memory, the refresh token
  of the active account and those of parked accounts in secure storage
  (`features/session/vault.ts`). Who is signed in: `features/session/store.ts`.
  Switching accounts, adding one, signing out: `features/session/session.ts`. Each starts the signed-in tree over (a new
  API object, realtime connection, query cache and navigation stack), the way
  a page load does on the web. A sign-out shows at once; the session's token
  is kept aside (`departed`) until the server has removed its push
  registrations and ended it, retried on each start when it was offline.
  Every use of a parked or departed token waits its turn, so none is ever
  sent twice.
- **Location.** The same rules as the web (`features/map/sharing.ts`): nothing
  is sent for an account until it says yes on this device; stopping, a
  revoked permission, a sign-out or a switch tell the server, and a stop that
  did not reach it is retried. On screen the position is watched and sent at
  the server's cadence (`reportDecision` in `@tokuly/core/map`); off screen,
  with "always" allowed, the background task sends what the OS delivers
  (50 m distance filter, deferred batches, paused while still).
- **Chat.** The rules are `@tokuly/core/chat`: realtime events go into the
  cache through `applyChatEvent` (`features/chat/sync.ts`), timelines page
  through `MessagePager`, the unread totals through `UnreadTotals`; the phone
  keeps only its live state (typing, read cursors) and its outbox (messages on
  their way, photos uploaded first through the media upload flow, sent in
  order with an idempotency key, retried by hand). Calls and the AI assistant
  stay on the web for now; the conversation says so and opens it.
- **Camera and uploads.** The camera is VisionCamera (`features/media/camera-screen.tsx`):
  a tap takes a photo, holding records (a short: a tap starts and stops), front or
  back, flash; the longest recording is the server's limit for the purpose
  (stories 60 s, shorts 3 min; every upload's answer brings the server's own),
  shown before anything is recorded. A library video that is longer is cut down
  first: the trim screen picks the part, and the local module
  `modules/tokuly-trim` cuts it on the device (Media3 Transformer on Android,
  AVAssetExportSession on iOS; no FFmpeg in the app). A story or a short is a _post_ (`features/media/posts.ts`):
  its files are copied into the app's documents, uploaded through the media flow
  (`features/media/upload.ts`: one presigned PUT, or the parts the store does not
  hold yet), then it is created. PUTs are the OS's own transfers (a background
  URL session on iOS); a post that was interrupted (no network, the app closed)
  goes on from where it stopped at the next start or return to the front. A post
  belongs to the account it was started as and is only ever sent as it: every
  request is made with that account's API and only while it is the active one, a
  switch stops it first (the feature's `lifecycle.ts`) and it goes on once that account is
  back; it is thrown away when that account leaves the device. A refusal shows
  the server's reason (MEDIA_TOO_LONG with the limit, in ja/en).
- **Stories.** The tray (above the chats) and the viewer come from
  `@tokuly/core/stories`: tap the sides to go back and on, hold to pause, swipe
  sideways between people and down to close; progress bars, a story counts as
  watched once it is really shown (`features/stories/seen.ts`), reactions, and
  replies, which are direct messages through the chat's outbox. The owner sees
  who watched. Stories go to every friend or to the close friends picked for
  that story (the story API's audiences).
- **Shorts.** A tab of its own: the three swipe feeds from `@tokuly/core/shorts`
  (its pages, cache edits and stay meter), one short a screen with expo-video
  (HLS), the next one loading ahead, sound on or off for the whole feed, likes
  (`@tokuly/core/engagement`), comments, the share sheet with the server's link,
  hashtag and sound pages, posting (record or pick, trim, caption with hashtag
  suggestions, who sees it: public, followers, friends, close friends, a circle,
  only me) and the creator's own list with what is still being processed or
  failed, and why.
- **Videos.** Long videos, from 「動画」 in the Me tab's hub, are
  `@tokuly/core/video` (keys, cache edits, feeds, the watch page's rules,
  playback reporting): the home, subscriptions and trending feeds with
  genre chips (holding a card: watch later, save, not interested), the
  watch screen with expo-video (HLS, native controls, full screen,
  picture-in-picture and the lock screen's controls, from the `expo-video`
  config plugin), starting where the viewer left off or at a link's `?t=`,
  chapters and description times that jump, likes, watch later, playlists,
  subscriptions with their notification level, comments, the playlist
  being played and "up next". Playback is reported as the account that
  opened the screen and ends with it (`features/video/playback.ts`, its
  `lifecycle.ts`); it counts while the picture is on the screen, in the app
  or its small window, not as sound behind another app. Channel pages,
  playlists, the history and the subscriptions list are native too;
  uploading, editing, analytics and watch parties open the studio on the web.
- **Live.** Watching is native (`features/live`, from 「ライブ」 in the Me tab's
  hub and from every `/live/<id>` link or push): friends on air, the channels
  the viewer subscribes to, everyone public, and what is scheduled. A stream
  plays as Low-Latency HLS in expo-video (AVPlayer and ExoPlayer play the
  partial segments natively; the app has no WebRTC stack, so WHEP stays the
  web's), opened again with fresh URLs when it fails, with the viewer's
  heartbeat (`ReportWatching`) while the app is in front. The rules and the
  cache are `@tokuly/core/live`: the stream's topic goes through `LiveChats`
  (lines, deletions, pins, highlighted gifts, polls, numbers, the end, a
  raid), lines of people the viewer blocked stay out, and the chat is read
  again after every gap without losing what was pushed meanwhile. Chat with
  mentions, slow mode and the server's reason when the viewer may not write;
  likes, sharing, reminders, votes, reports; gifts with the tier's colours
  and message length, a preview, a confirmation and one idempotency key per
  attempt (a gift whose answer was lost is repeated under its key, so
  nothing is paid twice). Going live stays on the web screen (`/studio/live`):
  the app has no WHIP or RTMP publisher, and the web's studio sets a stream
  up and publishes from the camera in the browser. So do the archive (a
  video), clips, the gift history, buying coins and the moderation tools.
- **Push.** The phones' own services through `expo-notifications`, no Expo push
  service: FCM on Android (the build needs `GOOGLE_SERVICES_JSON`, the path of
  the Firebase project's `google-services.json`), APNs on iOS
  (`EXPO_PUBLIC_APNS_ENV=production` for store builds). Like location sharing,
  push is the account's decision on this device (`features/notifications/push.ts`):
  the token is registered for an account's session only once it said yes here;
  before it signs out or another account takes over, its registration is
  removed (the server waits for a registration of that session still being
  written). When the server cannot be told, the token itself is thrown away
  and the removal is owed: each start tries again as that session, parked on
  the device, until it goes through — so the next account never gets the
  previous one's pushes. What a push shows
  on the lock screen is the account's preview setting, applied by the server;
  Android channels (one per category) keep the system's lock-screen rule. A tap
  opens the screen the notification is about (`features/notifications/target.ts`),
  the inbox otherwise.
- **Open-source notices** (Settings → licences, needed for the stores) are
  written at build time by `scripts/licenses.js`, which app.config.ts runs:
  every production dependency the app bundles with its licence and text, and
  the native libraries of the app's own modules (`modules/*/notices`). The
  output, `src/generated/licenses.json`, is not checked in.
- **Web screens.** What the app does not have yet (notes,
  spaces, communities, school, plans, ask, quests, emoji, stamps, the wallet,
  most settings, developers, the console) opens in a web view
  (`features/web`), signed in as the account in use. It plugs in through
  the seams: 「もっと見る」 in the Me tab's hub (`hub.ts`), the settings' web
  row (`settings-rows.ts`), and the web-only paths (`links.ts`), so pushes,
  inbox entries and deep links (`app/+not-found.tsx`) to them open there too. Signing the web view in is the
  identity domain's hand-off: the app asks for a one-time code as its own
  session (`CreateWebHandoff`, 60 seconds, once, bound to a verifier the
  web view's first load sends in a header, so a leaked link signs nobody in)
  and loads `/api/auth/handoff?code=…`, which sets the web session's cookie and goes on
  to the page; the app's tokens never reach the web view, and the web
  session ends with the app's. A code that comes back after another account
  took over is dropped. The web view is incognito and keyed by its account's
  session; everything web views stored (cookies, on disk too, localStorage,
  cache) is removed before one opens, when the last one closes
  (`open-screens.ts`: Android's web views share one store, and a screen
  that closes late must not take the next one's cookie), before every switch
  or sign-out and before a departed session ends (`lifecycle.ts`, with the
  local module `modules/tokuly-web-data`), and the app's own
  API calls send no cookies (`lib/api.ts`). Links to anywhere else open in the system
  browser. Features move out of `features/web/features.ts` and `links.ts`
  as they become native.

## How a feature plugs in

A feature never edits the tab bar, the signed-in layout, the hub, the settings
screen, the profile screen, the push targets or the session code. It adds a
file with a fixed name to its own folder and default-exports what it
contributes; `src/seams/*` collects the files (each type is documented
there). Two features can therefore be built side by side without touching the
same file.

| file in `src/features/<area>/` | default export                           | what it does                                                                  |
| ------------------------------ | ---------------------------------------- | ----------------------------------------------------------------------------- |
| `tabs.tsx`                     | `TabEntry[]` (`#/seams/tabs`)            | a tab; its route is `app/(app)/(tabs)/<name>.tsx`                             |
| `hub.ts`                       | `HubEntry[]` (`#/seams/hub`)             | the area's way in from the last tab, for what has no tab                      |
| `screens.ts`                   | `ScreenEntry[]` (`#/seams/screens`)      | how its routes under `app/(app)/` are presented: title, modal, no header      |
| `links.ts`                     | `LinkTarget[]` (`#/seams/links`)         | which of the server's paths (notifications, pushes) open which of its screens |
| `settings-rows.ts`             | `SettingsRow[]` (`#/seams/settings`)     | rows of the settings screen                                                   |
| `settings-card.tsx`            | `SettingsCard` (`#/seams/settings`)      | a control on the settings screen itself                                       |
| `badges.ts`                    | `BadgeSources` (`#/seams/badges`)        | unread counts by key, shown by the tabs that name the key                     |
| `background.tsx`               | a component (usually rendering nothing)  | runs on every screen while someone is signed in: realtime listeners, sync     |
| `lifecycle.ts`                 | `AccountLifecycle` (`#/seams/lifecycle`) | what it owes an account that leaves this device (see below)                   |
| `profile.tsx`                  | `ProfileSection[]` (`#/seams/profile`)   | what the area shows on a person's profile, by slot                            |

```tsx
// src/features/plans/tabs.tsx — with app/(app)/(tabs)/plans.tsx rendering the screen.
export default [
  { name: "plans", order: 35, title: () => i18n.t("plans:tab"), icon: CalendarHeart, badge: "plans" },
] satisfies TabEntry[];

// src/features/plans/badges.ts — the tab's counter.
export default { plans: () => useInvitations().data?.length ?? 0 } satisfies BadgeSources;

// src/features/plans/screens.ts — app/(app)/plans/new.tsx opens as a modal.
export default [
  { name: "plans/new", options: () => ({ title: i18n.t("plans:new"), presentation: "modal" }) },
] satisfies ScreenEntry[];

// src/features/plans/links.ts — a push about a plan opens it.
export default [
  { path: /^\/plans\/([^/]+)$/, screen: (match) => `/plans/${match[1]}` },
] satisfies LinkTarget[];
```

Routes stay files: Expo Router finds `app/(app)/plans/[id].tsx` by itself, and
a route file only renders a screen of the feature. A route without an entry in
`screens.ts` gets the default header.

**The registries.** Metro has no `import.meta.glob`, so `scripts/seams.js`
writes the list of each seam's files to `src/generated/seams/<seam>.ts`: from
`metro.config.js` (every bundle and dev server) and before `typecheck` and
`test`. They are not checked in, like the web's route tree: two branches that
both add a feature would always conflict there. After adding or removing a
seam file while Metro runs, `pnpm --filter @tokuly/mobile seams`; a jest run
on stale registries fails (`src/seams/__tests__/registry.test.ts`).
A file that carries a seam's name but would not be listed (deeper than the
feature's folder, not `.ts(x)`, no `export default`) stops the generator, and
with it the bundle: a `lifecycle.ts` left out would be a privacy hook that
never runs.
(`require.context` would do the same inside Metro, but it is still behind an
`unstable_` flag, jest needs a stand-in for it, and its result is untyped: a
generated import list is checked by `tsc` against each seam's type.)

### Accounts: the rules a feature follows

Several accounts live on one phone (a main one, a 裏垢, a creator account),
and one must never speak, be seen or be notified as another. Every switch,
added account and sign-out starts the signed-in tree over (components
unmount, the query cache is new), which takes care of what a feature shows.
What a feature _sends by itself_ is its own duty:

- **Capture the account before the first await.** `api()` is whoever is
  signed in _now_; after an await that may be someone else. Take
  `currentAccount()` (`features/session/account.ts`: session, user, the API
  object) or the client (`const client = pushClient()`) first, make every
  request of that piece of work with it, and after each await ask
  `isActive(account)` / `ensureActive(account)` before going on. State in
  secure storage is kept per user or session ID, never "the current one".
- **Leave in `lifecycle.ts`.** `beforeLeave(account)` runs while the leaving
  account's session still works (after a switch went through, before a
  sign-out reaches the server): stop sending, wait for what is in flight, tell
  the server. All features' hooks run together and each has 3 s; after that
  the account leaves anyway — and a hook left behind goes on running under
  the next account, so every request it makes goes through `account.api`
  (or a client taken before its first await), never `api()` after one.
  Nothing registers at run time: a hook is there whether or not a component
  was mounted.
- **Owed work.** What must reach the server and could not (offline, the 3 s
  ran out) is written down _before_ it is tried, by session or user ID, and
  retried until it goes through: at the next start as that account, or right
  away as the parked session with `asParked(sessionId, work)`
  (`features/session/parked.ts`), which resolves to `null` when the device
  no longer holds it. Push registrations (`features/notifications/push.ts`)
  and the stop of location sharing (`features/map/sharing.ts`) are the
  examples to copy.
- **Parked tokens go through the one queue.** A refresh token sent twice
  revokes its session. Nothing but `features/session` reads the vault's
  tokens; work as a parked account is `asParked`, which waits its turn
  behind switches and removals.
- **A session that left for good** (signed out offline, a previous install)
  is resumed once more before the server ends it: `beforeEnd(session)` takes
  back what the feature left on the server for it. Throwing keeps the session
  aside for the next start. What a feature keeps on the device for an account
  (a queue of posts) it drops once `accountsOnDevice()` no longer lists the
  session.

## Checks

```sh
pnpm --filter @tokuly/mobile typecheck
pnpm --filter @tokuly/mobile lint      # Biome, as the rest of the repository
pnpm --filter @tokuly/mobile test      # jest-expo + React Native Testing Library
pnpm --filter @tokuly/mobile export    # the JS bundles of both platforms
```

Logic is tested in the shared packages (Vitest). Component tests here cover
the screens that matter and mock only the edges: the network (`expo/fetch`),
device modules, the clock.

The Maestro flows (`maestro/flows`) sign up and in, switch accounts, accept a
friend and see them on the map, use ghost mode and sharing, open a chat with an
unread message, send one, receive one from a second account (through the API),
start a chat and open the inbox, post a story from the library and watch it as
a friend (the emulator has no camera: the pictures are put in its library, and
the camera is covered by a component test), post a short, swipe the feed and
like it, open the video feeds and subscribe to a channel (playback is covered
by the watch screen's component test: a flow's script cannot upload a video),
find a friend's scheduled stream, ask for its reminder and chat before it
starts, open a web-only feature from 「もっと見る」 and see it signed in. CI
(the End to end workflow, `.github/workflows/e2e.yml`) builds a release APK for the emulator and
runs them against the Compose stack; locally, with an emulator and a stack:

```sh
EXPO_PUBLIC_TOKULY_URL=http://10.0.2.2 pnpm --filter @tokuly/mobile android --variant release
pnpm --filter @tokuly/mobile e2e --env SERVER=http://localhost   # the scripts run on the host
```
